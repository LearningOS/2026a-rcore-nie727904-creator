# Lab 2 实验报告：地址空间

## 一、实验目标

本次实验基于 rCore 第四章的 Sv39 虚拟内存机制，完成用户态系统调用与内存映射管理。

主要任务包括：

1. 实现 sys_get_time，使内核能够向用户虚拟地址写入时间信息。
2. 实现 sys_trace，支持用户内存字节读写及系统调用次数统计。
3. 实现 sys_mmap，为用户进程建立指定权限的虚拟内存映射。
4. 实现 sys_munmap，解除用户进程的虚拟内存映射并回收物理页。
5. 使用官方 Checker 验证实现结果。

## 二、实验环境

- 操作系统：Ubuntu 22.04.5 LTS（WSL2）
- 开发语言：Rust
- 目标架构：riscv64gc-unknown-none-elf
- 模拟器：QEMU 8.2.2
- 实验分支：ch4
- 测试工具：rCore-Tutorial-Checker

## 三、实验实现

### 3.1 sys_get_time

第四章引入虚拟地址空间后，用户程序传递给内核的指针属于用户虚拟地址，不能简单地按照物理地址进行解引用。

本实验调用 get_time_us 获取当前时间，并计算秒数与微秒数：

- sec = us / 1000000
- usec = us % 1000000

随后将 TimeVal 的两个字段转换为字节，通过 translated_byte_buffer 将用户虚拟地址对应的内存划分为物理页内的缓冲区，再逐段复制。

这种方法能够处理 TimeVal 跨越两个虚拟页面的情况，避免假设用户缓冲区在物理内存中连续。

### 3.2 sys_trace

本实验实现了三种 trace 请求：

- 请求 0：读取用户虚拟地址中的一个字节。
- 请求 1：向用户虚拟地址写入一个字节。
- 请求 2：查询当前任务指定系统调用的调用次数。

对于读写请求，使用当前任务的页表令牌构造 PageTable，并通过 translate 查询虚拟页对应的页表项。

访问前检查页表项是否有效，以及是否具备用户态访问权限和相应的读写权限。

对于系统调用次数统计，在 TaskControlBlock 中保存每个任务独立的 syscall_counts 数组，并在系统调用分发前更新对应的计数器。

这样可以避免不同任务之间相互干扰，同时使 trace 能够查询当前任务的系统调用次数。

### 3.3 sys_mmap

sys_mmap 用于在当前任务的虚拟地址空间中建立匿名内存映射。

实现时主要进行以下处理：

1. 检查起始地址是否按页面大小对齐。
2. 检查 prot 参数是否合法。
3. 检查地址范围计算是否发生溢出。
4. 遍历目标虚拟页面，检查是否与已有有效映射冲突。
5. 根据 prot 构造对应的用户页面权限。
6. 使用 MemorySet 中的页帧映射机制分配物理页并建立页表映射。

实现中先检查完整目标范围，再执行实际映射，避免由于中途发现地址冲突而产生部分映射。

每个页面由独立的 MapArea 管理，便于后续解除部分页面映射。

### 3.4 sys_munmap

sys_munmap 用于解除当前任务指定范围内的页面映射。

实现过程包括：

1. 检查起始地址及长度是否合法。
2. 遍历页面范围，确认待解除的页面存在。
3. 在检查通过后，从 MemorySet 中移除对应的 MapArea。
4. 通过 MapArea::unmap 清除页表项。
5. 通过 FrameTracker 的资源管理机制回收对应物理页帧。

该实现避免了在尚未检查全部页面时就直接修改页表，从而降低部分解除映射造成地址空间状态不一致的风险。

### 3.5 任务地址空间管理

通过 TaskManager 为当前运行任务提供 mmap、munmap 及系统调用计数接口。

相关操作通过 UPSafeCell 的 exclusive_access 获取任务管理器内部数据，并访问当前任务的 TaskControlBlock。

映射和解除映射只影响当前任务的 MemorySet，实现任务之间的虚拟地址空间隔离。

### 4.3 测试结果分析

最初系统调用仍为占位实现，导致时间读取、trace 和内存映射测试失败。

实现 sys_get_time 后，时间与休眠相关测试恢复正常。

实现 sys_trace 后，基础 trace 测试通过；后续 trace 测试还依赖 mmap 创建只读映射，因此需要完成内存映射功能才能通过。

在完成 mmap 和 munmap 并接入当前任务地址空间后，Checker 的 16 项功能检查全部通过。

## 五、问题与思考

### 5.1 为什么不能直接解引用用户指针？

第四章中用户程序和内核使用不同的地址空间，用户传入的地址必须经过当前任务的页表转换才能定位到实际物理页。

直接解引用用户虚拟地址可能访问错误位置，也不能正确处理跨页缓冲区。

### 5.2 为什么映射之前必须先检查地址范围？

如果在逐页映射的过程中才发现某个页面已经被映射，直接使用底层 map 接口可能引发断言失败。

因此需要先检查所有目标页面，再进行映射操作。

### 5.3 为什么解除映射还需要回收物理页？

页表映射关系和物理页所有权是不同的资源。

如果只删除页表项而没有释放对应的 FrameTracker，物理页仍可能被占用，造成资源泄漏。

### 5.4 实现的局限性

当前 mmap 实现采用逐页 MapArea 管理，便于部分解除映射，但会增加地址空间管理中的区域对象数量。

此外，当前实现尚未为匿名 mmap 页面建立与其他用户区域完全独立的所有权标记，更严格的边界测试还可以进一步完善。

## 六、实验总结

本次实验完成了 rCore 第四章中时间系统调用、trace、匿名内存映射与解除映射功能。

通过实验，理解了 Sv39 页表、虚拟地址到物理地址的转换、用户态访问权限检查，以及 MapArea 和 FrameTracker 在内存管理中的作用。

最终官方 Checker 功能测试结果为 16/16，达到本次实验的功能测试目标。
